## 背景

项目当前还是一个空白的 OpenSpec 工作区，目标是演进成面向个人分散照片库的照片管理平台。目标主流程是：从多个来源导入照片与视频，把原始文件落到对象存储中，通过异步流程补齐元数据和 AI 识别结果，再按时间、地点和内容把资产检索出来，同时通过备份和导出保留独立恢复路径。

这个变更是一个典型的跨层设计，因为它同时引入了存储抽象、统一资产模型、异步处理、搜索索引和用户可见的发现能力。设计上需要兼顾两点：第一版 MVP 不能太重，后续又要保留扩展更多存储 Provider、AI Provider 和前端客户端的空间。

主要相关方包括：
- 终端用户：希望把分散在不同设备和平台里的照片收拢到一个可信主库。
- 运维或部署者：需要可预测的存储、备份和 Provider 配置方式。
- 后续贡献者：需要稳定的内部契约来扩展存储、AI 识别和检索能力。

## 目标 / 非目标

**目标：**
- 定义照片资产、派生资源、元数据、识别状态和备份状态的统一领域模型。
- 将核心职责拆分为存储、元数据、识别增强、检索发现和备份层，并暴露清晰接口。
- 支持可插拔的对象存储和 AI Provider，同时避免把厂商特有返回结构泄漏到领域模型中。
- 支持一版可落地的实现，至少覆盖上传、后台识别、混合搜索和已验证备份。
- 在首版中优先采用模块化单体加后台 Worker，而不是一开始就拆成多个服务。

**非目标：**
- 首版不做原生移动端应用。
- 首版不做实时协作分享、评论或社交网络能力。
- 首版不追求人脸识别和实名管理的完美能力。
- 首版不通过非官方接口做 QQ 空间等封闭平台的实时同步。
- 首版不默认引入独立搜索集群，除非 PostgreSQL 方案无法满足需求。

## 设计决策

### 决策：采用模块化单体，并拆分 API 进程与 Worker 进程
第一版实现采用一个代码库、两个运行角色：API 进程负责导入、配置和检索请求，Worker 进程负责异步识别和备份任务。这样可以降低系统拆分带来的协作和运维成本，同时避免长耗时的 AI 与复制任务影响请求延迟。

备选方案：
- 一开始就做微服务：不采用，因为当前没有现成的规模压力，过早拆分会拖慢 MVP 落地。
- 上传时同步完成所有识别：不采用，因为 AI、OCR 和地理反解延迟会让上传流程变慢且脆弱。

### 决策：以 PostgreSQL 作为元数据和检索编排的事实来源
PostgreSQL 用来存储统一资产记录、导入会话、Provider 配置、识别状态、相册关系和备份元数据。MVP 阶段默认结合 `pgvector` 做语义相似度，结合 PostgreSQL 全文检索 captions、OCR 文本和 tags，从而在不引入外部搜索集群的前提下提供混合搜索能力。

备选方案：
- 首版直接引入 Elasticsearch 或 OpenSearch：不采用，因为运维成本较高，对 MVP 规模并非刚需。
- 只把可检索信息存到对象存储 metadata：不采用，因为跨 Provider 查询能力过弱，而且不同厂商行为不一致。

### 决策：持久化 Provider 无关的资产身份与对象引用
每个资产都拥有统一的 `asset_id`、内容哈希、感知哈希，以及一组对象引用。对象引用负责记录 Provider 名称、bucket 或 container、对象 key、版本或 etag，以及 `original`、`thumbnail`、`preview` 等用途。系统不会把 Provider 的原始响应体当作事实来源。

备选方案：
- 直接把 Provider key 当作主标识：不采用，因为这会让迁移、备份和多 Provider 支持变得脆弱。
- 每个资产只保留一条原图路径：不采用，因为备份、导出和恢复流程都需要维护多个对象引用。

### 决策：将 AI 返回结果归一化为内部识别记录
不同 AI Provider 的返回结构差异很大，因此 Worker 层必须将其映射为统一的识别记录，例如 captions、tags、OCR blocks、embeddings，以及可选的人脸或主题聚类。Provider 原始响应可以保留用于调试，但发现层和后续流程只能依赖归一化字段。

备选方案：
- 直接以 Provider 返回结构作为主元数据：不采用，因为 Provider 间 schema 漂移会把复杂度扩散到检索、备份和导出逻辑里。
- 首版只支持单一 AI 厂商：不采用，因为隐私、成本和地区可用性本来就是这个产品的重要约束。

### 决策：采用分阶段、可重试、幂等的后台任务状态机
资产处理按明确阶段推进，例如 `accepted`、`stored`、`derivatives_ready`、`metadata_ready`、`ai_ready`、`indexed` 和 `partial_failure`。每个后台任务都必须幂等且可重跑，确保重试不会产生重复对象或重复元数据记录。

备选方案：
- 用一个大而全的“处理资产”任务串行完成全部步骤：不采用，因为部分失败的恢复路径会变得不透明。
- 后台任务只做 best-effort，不跟踪状态：不采用，因为用户需要看到索引进度，运维也需要确定性的重试机制。

### 决策：通过统一查询模型实现混合发现
发现层查询会把结构化过滤、全文匹配和向量相似度整合到一个查询服务中。查询层根据可用信号生成综合排序，并在某个资产尚未完成全部识别阶段时做平滑降级。

备选方案：
- 把元数据搜索和语义搜索拆成两个独立接口：不采用，因为用户应该能用一句自然语言完成一次完整检索。
- 未完成识别的资产全部从浏览和搜索结果中隐藏：不采用，因为刚上传的照片也必须立即出现在主库视图里。

### 决策：把备份当作一等工作流，而不是额外附加项
备份要被建模为独立的复制工作流，拥有自己的目标 Provider、manifest 条目、校验状态和重试历史。只有当复制副本通过源资产身份与完整性校验之后，资产才会被标记为已受保护。

备选方案：
- 完全依赖主存储自身的高可用：不采用，因为用户诉求本身就要求独立恢复路径。
- 只提供手动导出，不做持续复制：不采用，因为手动导出无法及时保护新增资产。

### 决策：导入来源保持明确且可控
MVP 支持上传、本地目录导入和历史导出包导入。像 QQ 空间这类封闭平台，首版只支持用户自行导出后再导入，不做非官方在线抓取，从而降低维护成本和法律风险。

备选方案：
- 首版就为所有消费级平台做直接同步适配器：不采用，因为脆弱的非官方集成会过早吞掉项目精力。

## 风险 / 权衡

- [仅使用 PostgreSQL 的混合搜索效果可能不够强] -> 缓解：保留搜索适配层边界，后续可以无痛接入独立搜索引擎。
- [大规模照片库下 AI 调用成本可能快速上升] -> 缓解：记录每个任务的 Provider 选择，允许关闭高成本阶段，并支持按相册设置本地优先策略。
- [后台任务重试如果设计不当会造成状态不一致] -> 缓解：强制任务幂等，显式维护阶段迁移，并在写入前做对象级身份校验。
- [地理反解和 AI 识别会带来隐私风险] -> 缓解：允许按任务类型配置 Provider 策略，支持仅本地处理，并阻止敏感资产发送到不允许的外部 Provider。
- [大批量导入时备份副本可能明显滞后] -> 缓解：在资产模型里暴露备份状态，只有通过校验后才标记为已保护。
- [历史来源较乱时元数据可能不完整] -> 缓解：保留导入时间戳和来源信息，让发现层优先使用“最佳可用时间”而不是让导入失败。

## 迁移计划

1. 引入统一数据库 Schema、Provider 配置模型和对象引用模型。
2. 实现主导入流程，完成上传和批量导入、原始对象持久化以及派生资源生成。
3. 增加 Worker 驱动的元数据提取、AI 识别和索引更新，并暴露清晰处理状态。
4. 增加时间线、地点浏览、重复照片审查和混合搜索等发现能力。
5. 增加二级备份复制、完整性校验、导出清单和恢复导向的打包能力。

回滚策略：
- 关闭新的导入入口，同时保留已存储的原图和元数据。
- 停止 Worker 消费，冻结识别和备份流程，而不删除源资产。
- 如果后续需要重构，可先从 PostgreSQL 导出已保存的元数据和对象引用。

- 默认参考实现优先接入哪类 AI Provider：云端多模态 API、本地模型流水线，还是两者都做？
- 首个用户可见客户端需要完整的 Next.js 应用，还是一个偏管理台风格的上传与浏览界面就足够？
- 首版备份复制只支持完整副本目标，还是要同时覆盖归档层和生命周期策略目标？
