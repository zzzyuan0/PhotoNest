## Context

当前仓库已经具备导入会话、上传票据签发、浏览器直传对象存储、上传确认、时间线/地点浏览和资产详情接口的最小实现，`db/migrations` 与 `db/queries` 也已经为 PostgreSQL 持久化预留了结构。但是运行时主链路仍有几个关键断点：

- `internal/ingestion` 默认仍回落到 `NewMemoryStore()`，导入会话、资产、对象引用和识别状态不会写入 PostgreSQL。
- `internal/enrichment` 仍使用进程内 `MemoryQueue`，Worker 进程没有消费逻辑，导致增强任务只存在于 API 进程内存里。
- `PUT /api/v1/settings/providers/{providerName}` 未实现，真实 COS 配置难以通过应用接口更新和校验。
- Web 导入页在收到 `multipart` 票据时直接报错，无法覆盖大文件或必须走分片上传的场景。
- 发现链路虽然已有列表与详情接口，但上传后的“可查看性”依赖内存状态，缺少服务重启后仍可稳定读取的新鲜资产路径。

这个变更横跨配置、存储、异步处理、HTTP API 和 Web 上传体验，属于典型的跨模块主流程收口工作。相关方包括：

- 使用者：需要在真实 COS 环境中把图片传上去并马上在 Web 中看到它。
- 运维/部署者：需要一个可验证、可重启、不会因为进程退出就丢状态的部署路径。
- 后续贡献者：需要明确哪些行为属于“主流程必须保证”的契约，避免继续堆叠仅适用于 demo 的实现。

## Goals / Non-Goals

**Goals:**

- 让导入会话、资产、对象引用和基础识别状态以 PostgreSQL 为事实来源，保证服务重启后上传与查看状态不丢失。
- 让上传确认后的增强任务进入 Redis 队列，并由独立 Worker 进程真实消费，完成后台处理闭环。
- 让 Web 端在小文件直传和大文件 multipart 上传两种场景下都能完成 COS 上传与确认。
- 让新上传资产在确认后能够稳定出现在总览、时间线和资产详情查看流程中，即使后台增强尚未全部完成。
- 让 COS Provider 配置可以通过设置接口更新并完成可操作的连通性校验与脱敏返回。
- 为以上行为补齐集成测试和端到端验证基线。

**Non-Goals:**

- 本次不补齐 `POST /api/v1/assets/batch-downloads`，因为它不是“上传到 COS 并查看”主链路的阻断项。
- 本次不扩展新的 AI Provider 类型，也不引入新的识别阶段，只修复现有异步处理能够真正运行。
- 本次不处理历史内存数据向 PostgreSQL 的迁移；默认把当前系统视为开发阶段，切换后以新环境重建数据为主。
- 本次不设计新的移动端或桌面端导入器能力。

## Decisions

### 决策：以 PostgreSQL 仓储替代运行时默认内存仓储

主流程所需的导入会话、导入条目、资产、对象引用、识别阶段运行记录和备份目标映射统一落到 PostgreSQL，API 与 Worker 共享同一仓储实现。内存仓储仅保留给单元测试或无数据库依赖的局部验证，不再作为生产或默认开发运行路径。

这样做的原因是：当前最大的功能断点不是“有没有接口”，而是状态事实来源不可靠。只要仓储仍在内存里，上传确认、查看、队列消费和服务重启恢复都无法形成稳定契约。仓库里已经存在 migration 和 query 定义，直接接上 PostgreSQL 的成本低于继续扩展 MemoryStore 的补丁式逻辑。

备选方案：

- 继续以 `MemoryStore` 为默认实现，仅在特定模式下启用 PostgreSQL：不采用，因为会继续放大环境差异，主流程问题会在不同运行方式之间反复出现。
- 先做文件型本地持久化再切数据库：不采用，因为仓库已经为 PostgreSQL 建好了数据模型，额外引入中间方案只会增加维护负担。

### 决策：以 Redis 持久队列 + 独立 Worker 完成增强任务闭环

上传确认后，API 只负责把任务写入 Redis 队列；独立 Worker 进程从 Redis 拉取任务并执行派生资源生成、元数据提取和识别状态推进。队列消息必须带稳定任务键、资产标识和阶段信息，Worker 消费逻辑必须幂等，允许重试与重启恢复。

这样做的原因是：当前 `MemoryQueue` 让任务生命周期绑定在 API 进程上，Worker 形同虚设，上传后后台处理无法跨进程工作。既然配置里已经有 Redis 地址，最直接的修复就是让 API 和 Worker 真正通过 Redis 解耦。

备选方案：

- 保持进程内队列，只在 API 启动 goroutine 后台消费：不采用，因为这仍然无法满足独立 Worker、重试恢复和进程隔离的要求。
- 一次性引入 Temporal 等工作流引擎：不采用，因为当前缺口是“从没有到可用”，先用 Redis 队列补齐 MVP 更符合投入产出。

### 决策：上传确认后即保证“可查看”，增强结果异步补齐

系统以“对象已上传并校验通过、资产记录已持久化、基础对象引用可读”为查看链路的最小门槛，而不是把“所有增强阶段完成”作为图片出现在总览或详情页的前置条件。时间线列表、总览卡片和资产详情必须在识别处理中仍能返回该资产，同时明确暴露处理中状态。

这样做的原因是：用户对“上传成功”的直觉是马上能看到照片，而不是等待所有后台任务跑完。当前已有发现规格也支持“处理中资产仍可见”，这次需要把它落实到持久化和 API 返回行为上。

备选方案：

- 只有缩略图和索引都生成后才展示资产：不采用，因为会让刚上传的资产看起来像“上传失败”。
- 确认后直接暴露原始对象公网 URL：不采用，因为这会破坏默认私有读和受控访问边界。

### 决策：保持服务端主导的 COS 上传状态机，并补齐 Web 端 multipart 流程

上传对象 key、预签名参数、multipart 初始化信息和完成确认全部继续由服务端生成与校验。Web 端根据票据自动选择单次 PUT 或 multipart 上传，不把 COS 特有参数散落到页面逻辑中；上传完成后统一调用确认接口，提交 etag、uploadId 和分片结果。

这样做的原因是：当前后端已经具备 `multipart` 票据规划能力，但前端直接报“不支持分片”，导致大文件主流程断在浏览器端。保持服务端主导状态机可以继续保障对象 key 不透明、签名最小授权和确认校验的一致性。

备选方案：

- 让前端自行拼装 COS multipart 协议细节：不采用，因为这会让对象存储细节泄漏到 UI 层，后续维护和替换 Provider 都会更难。
- 上传阶段回退为服务端代理文件流：不采用，因为会放大 API 带宽与内存压力，也背离当前直传设计。

### 决策：Provider 设置更新接口以“校验后切换”为原则

`PUT /api/v1/settings/providers/{providerName}` 应支持更新 COS Provider 的可编辑字段，并在持久化或应用前完成凭据脱敏、参数归一化和连通性校验。只有当新配置通过 bucket 访问与必要权限检查后，系统才将其标记为生效配置；失败时返回可操作的错误分类，但不暴露秘密值。

这样做的原因是：真实联调时，配置入口缺失会迫使使用者改本地文件或重启服务，不利于验证和运维；同时如果接口只是盲写配置而不校验，也会让上传失败延迟到真正导入时才暴露。

备选方案：

- 继续只支持文件配置：不采用，因为用户已经明确希望修通完整流程，Provider 设置属于主链路前置条件。
- 接口接受配置后不立即校验：不采用，因为会把错误发现推迟到上传阶段，排障体验更差。

## Risks / Trade-offs

- [PostgreSQL 仓储替换涉及多个领域接口] → 通过保留仓储接口、分模块替换实现，并优先补齐导入、发现、增强相关集成测试来降低回归风险。
- [Redis 队列引入后，任务幂等性问题会暴露] → 为任务定义稳定幂等键，Worker 在写库前检查当前阶段状态，避免重复生成记录或重复推进状态。
- [multipart 上传前后端协作复杂，容易出现 etag/part 序号不一致] → 统一以后端票据为真，前端只回传后端要求的字段，并通过 HTTP 测试覆盖完成提交流程。
- [Provider 设置更新可能与启动时文件配置产生双来源冲突] → 明确运行时优先级，并在设计中限定“数据库中的运行时 Provider 配置覆盖静态文件中的同名 Provider”，同时保留回滚策略。
- [上传后立即可查看会让部分缩略图尚未生成的资产使用原图或占位图] → API 返回显式处理状态，前端对缩略图未就绪时使用受控占位展示，避免把处理中误判为失败。

## Migration Plan

1. 保持现有 migration 作为基础，补齐仓储实现与启动接线，让 API/Worker 默认连接 PostgreSQL。
2. 在数据库可用的环境中部署新版本 API，但暂时保留内存实现只给测试使用，不作为默认路径。
3. 部署 Redis 队列实现与 Worker 消费循环，验证新上传资产会在 Redis 中排队并被 Worker 消费。
4. 上线 Provider 设置更新接口与 Web multipart 上传支持，在预发或本地联调环境中用真实 COS bucket 验证上传与查看闭环。
5. 若新队列或新仓储出现阻断问题，可临时回滚到上一版本 API/Worker；由于当前阶段默认无生产持久化数据，回滚重点是服务可用性而不是数据迁移。

## Open Questions

- 运行时 Provider 设置最终写入数据库、配置文件映射，还是先写数据库并在启动时合并读取？当前建议以数据库作为运行时事实来源，但需要实现阶段确认优先级。
- 列表与详情页在缩略图尚未生成时，是否统一回退到受控原图预览句柄，还是返回固定占位图并等待刷新？当前建议列表用占位图，详情页可提供受控原图查看。
- Redis 队列实现是引入成熟库还是基于现有 `Queue` 接口补一个轻量实现？当前建议优先复用现有接口形状，避免在这次变更中同时重构全部任务模型。
