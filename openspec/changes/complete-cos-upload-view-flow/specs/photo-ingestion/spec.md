## ADDED Requirements

### Requirement: 导入会话与资产记录必须持久化到 PostgreSQL
系统 MUST 将 Web 上传流程中的导入会话、导入条目、资产记录和对象引用持久化到 PostgreSQL，并在 API 进程重启后仍可根据这些记录完成确认、查询和查看链路。

#### Scenario: 上传确认后服务重启
- **WHEN** 某个上传已经完成确认并写入对象引用，随后 API 进程重启
- **THEN** 系统仍然可以从 PostgreSQL 读取该导入会话和资产记录，并允许用户继续在总览、时间线或详情页查看该资产

### Requirement: Web 上传必须同时支持单次上传与 multipart 上传
系统 MUST 根据服务端返回的上传票据，在 Web 客户端同时支持单次直传和 multipart 直传到 COS，并在上传完成后统一调用确认接口闭合状态机。

#### Scenario: 小文件走单次上传
- **WHEN** 服务端返回 `multipart=false` 的上传票据
- **THEN** Web 客户端使用票据中的方法、URL 和请求头完成单次上传，并在成功后提交确认请求

#### Scenario: 大文件走 multipart 上传
- **WHEN** 服务端返回带有 `uploadId` 和分片列表的 multipart 上传票据
- **THEN** Web 客户端按票据顺序上传各分片、收集每个分片的 etag，并在全部完成后提交包含 `uploadId` 与分片结果的确认请求

### Requirement: 上传确认必须校验对象并创建可查看资产
系统 MUST 在确认阶段验证对象存在、大小、校验值和会话元数据一致后，才创建或更新正式资产记录；确认成功后的资产必须具备后续查看所需的最小对象引用与处理状态。

#### Scenario: 对象校验通过后创建正式资产
- **WHEN** 客户端提交的确认请求与对象存储中的实际对象信息一致
- **THEN** 系统将该对象登记为正式资产的原始对象引用，并把资产状态推进到可被发现接口读取的阶段

#### Scenario: multipart 完成信息不一致
- **WHEN** 客户端提交的 `uploadId`、分片 etag 或对象校验值与服务端预期不一致
- **THEN** 系统拒绝确认该上传，并保持导入条目处于失败或待重试状态，而不会创建错误资产记录
