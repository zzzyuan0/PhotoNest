## Context

当前项目已经具备一条相当完整但仍不够“用户可确认”的技术骨架：

- `apps/web/pages/login.vue`、`apps/web/pages/import.vue`、`apps/web/pages/index.vue` 中的大多数按钮都已经绑定到真实动作，能够触发登录、读取会话、创建导入会话、申请上传票据、确认上传、刷新时间线、搜索、收藏、加入相册与导出。
- `internal/ingestion/service.go` 在上传确认后已经会创建资产记录、生成缩略图与预览图引用，并把资产推进到 `derivatives_ready`。
- `internal/enrichment/service.go` 已经具备元数据提取、caption、OCR、embedding、索引更新等异步阶段，并会把资产状态推进到 `metadata_ready`、`ai_ready` 或 `indexed`。
- `cmd/worker/main.go` 已经具备消费 Redis 队列并运行识别增强的主循环。
- `internal/discovery/service.go` 与 HTTP handlers 已经能返回时间线、搜索、地点、重复候选、相册和资产详情。

但从用户视角看，现状依然有几处关键断裂：

- “按钮没反应”的主要原因往往不是没有实现，而是缺少显式反馈。例如收藏、加入相册、创建相册、导出等动作完成后没有统一成功提示；请求失败时多数只落在顶部 `error` 文案，用户不容易把失败和自己刚刚点击的按钮对应起来。
- 导入页虽然会把文件送到 `/api/v1/import/*`，但完成后只知道“进入照片库”，没有明确告诉用户识别和分类结果还会继续在后台推进到什么阶段。
- 首页能够显示 `processingStage` 和 `captionPreview`，但“分类”目前只是由 `locationLabel`、`tags`、收藏相册、手动相册、搜索文档与 embedding 支撑的整理能力，并没有一个面向用户的“识别结果总览”区域，因此用户很难确认系统是否真的完成了识别分类。
- 当前 AI Provider 默认是 `deterministic` 实现，它能生成可测试的 caption/OCR/embedding，但并不代表已经具备真实生产级视觉分类能力；如果不把这一点写进规格和设计，后续实现很容易在“有状态推进”与“有真实识别价值”之间混淆。

这次 change 的相关方包括：

- 使用者：希望点击按钮后能知道系统正在做什么、做成了什么、接下来去哪看结果。
- 开发者：需要知道哪些按钮已经有后端契约，哪些只是 UI 占位，避免重复造轮子或误判缺口。
- 测试与验收人员：需要一条可验证的标准，判断当前项目距离“上传照片 -> 识别 -> 分类”完整功能还差哪些必补项。

## Goals / Non-Goals

**Goals:**

- 明确当前 Web 端关键按钮的行为契约，让每个按钮在成功、失败、禁用和处理中都有可感知反馈。
- 把“上传确认成功”与“后台识别分类仍在继续”这两层状态拆开定义，避免用户把异步处理中误解为按钮无效或功能缺失。
- 明确当前版本中“识别分类”的最小定义，包括元数据、地点、caption、OCR、tags、搜索索引、收藏和相册等整理结果。
- 要求前端提供面向当前资产的状态说明与结果可见性，而不仅仅显示技术阶段字符串。
- 为后端、Worker 与前端联调补充端到端验收基线，能判断一张照片是否真的从上传走到了可搜索、可整理、可解释的状态。

**Non-Goals:**

- 本次不把“分类”扩展为人脸识别、主题聚类、自动智能相册、事件分组或多模态高级理解。
- 本次不要求彻底重写已有上传、识别或发现接口，只在必要时补充行为和返回信息。
- 本次不把所有按钮都改造成复杂工作流，重点只放在用户高频且目前容易产生“没反应”误判的动作。
- 本次不承诺把 `deterministic` Provider 直接替换成真实视觉模型，但要为后续替换保留一致契约。

## Decisions

### 决策：把“按钮是否实现”和“按钮是否给出足够反馈”明确分成两个问题

设计上不再把“点击没有反应”直接等同于“功能未实现”。现有页面中，登录、导入、刷新、搜索、收藏、加入相册、创建相册、导出等按钮大多已经连到后端；真正要补的是动作级反馈层，包括：

- 按钮触发时的局部 loading 或状态文案；
- 动作完成后的成功确认；
- 与按钮强关联的错误提示；
- 因前置条件不满足而禁用时的原因说明。

这样做的原因是：如果不先区分“未接线”和“反馈不足”，实施时很容易重做已有接口，而忽略真正让用户感知为“没反应”的交互空洞。

备选方案：

- 把所有按钮统一视作可能未实现，逐个补接口：不采用，因为现有仓库中大部分关键接口已经存在。
- 只在全局顶部显示错误或状态：不采用，因为用户无法把状态与刚刚触发的动作对应起来。

### 决策：把完整功能拆成“上传可见闭环”和“识别分类完成闭环”两层验收

一张照片的完整生命周期需要至少经过两道对用户可见的里程碑：

1. 上传可见闭环：文件经导入会话、上传票据、确认上传后，资产必须能在列表或详情中被看见，即使仍在处理中。
2. 识别分类完成闭环：后台异步阶段推进到足够完成的状态，用户能够通过 caption、OCR、地点、标签、搜索、收藏或相册等方式看见整理结果。

这样做的原因是：上传成功后立刻可见，是用户的第一预期；识别分类完成则是第二预期。把两者混为一谈会让“已经成功入库但尚未完成识别”的照片看起来像坏掉了。

备选方案：

- 只有全部识别完成后才在前端展示：不采用，因为会让新上传资产像是消失。
- 上传确认后就宣称“分类已完成”：不采用，因为这与当前后台异步设计不符，也会误导验收。

### 决策：当前版本把“分类”定义为可落地的整理能力，而不是超出仓库现状的高级智能语义

本次 change 采用保守但可执行的分类定义：

- 结构化元数据分类：拍摄时间、设备、尺寸、媒体类型。
- 地点分类：GPS 与 `locationLabel`。
- 文本识别与描述分类：caption、OCR。
- 检索与标签分类：`tags`、`searchDocument`、`embedding`、搜索结果。
- 人工整理分类：收藏相册、用户自建相册。

这样做的原因是：仓库当前已经有这些能力或字段，且 discovery 层已经围绕它们实现了搜索和整理。若在规格中直接要求“自动主题分类”“人脸聚类”等超出现状的能力，会把这次 change 变成全新产品定义，而不是对当前差距的真实收口。

备选方案：

- 把分类限定为仅有 AI 标签：不采用，因为当前整理能力还包括地点、相册和搜索索引。
- 直接要求高级视觉理解：不采用，因为与当前仓库现状和可实施范围不匹配。

### 决策：前端围绕“当前选中资产”展示识别状态与整理结果

首页详情区已经有右侧面板雏形，本次设计要求继续沿着这条路径收口，而不是另起一套结果中心页面。当前选中资产附近至少要能看见：

- 当前处理阶段；
- 是否已有预览；
- 是否已有 caption/说明；
- 是否已经可搜索或可加入整理流程；
- 若仍在处理中，下一阶段是什么；
- 若失败，失败的是哪一类能力，以及用户还能做什么。

这样做的原因是：用户在浏览和判断系统是否“识别分类成功”时，关注点天然是“这张我刚上传或刚点开的照片现在怎么样了”。把状态分散到多个区域会再次制造“按钮没反应”的体感。

备选方案：

- 专门做一个全局后台任务页展示所有状态：暂不采用，因为不能替代当前资产上下文中的即时反馈。
- 只显示原始技术状态值：不采用，因为用户无法理解这些状态意味着什么。

### 决策：验收必须同时覆盖 API/Worker 真实推进与 Web 可见结果

本次 change 在任务层面要求同时验证三段：

- API：上传确认后是否返回正确的已接收状态与资产标识。
- Worker：是否把资产从 `derivatives_ready` 推进到 `metadata_ready`、`ai_ready` 或 `indexed`。
- Web：按钮点击后是否有明确反馈，且资产状态/识别结果是否在页面上变得可见。

这样做的原因是：只测后端会遗漏“用户看不到”；只测前端又可能把模拟数据当成真实闭环。完整功能的判断必须横跨两端。

备选方案：

- 只补前端按钮测试：不采用，因为无法证明后台识别分类真的在推进。
- 只补后端状态机测试：不采用，因为无法解释用户为什么仍觉得“没反应”。

## Risks / Trade-offs

- [把很多“未反馈”问题归类为交互问题后，容易低估后端缺口] → 通过在 specs 中同时定义按钮反馈和后台闭环，避免只修 UI 不修主链路。
- [把当前分类定义得过于保守，可能让后续高级能力显得缺席] → 在规格中明确这是“当前版本最小闭环”，为后续自动主题/人脸等扩展留口子。
- [要求更多局部状态提示，会增加页面状态管理复杂度] → 优先围绕高频动作建立统一反馈模式，而不是为每个按钮单独发明一套状态机。
- [不同环境下 AI Provider 结果差异较大，验收标准可能不稳定] → 验收以阶段推进、字段可见性和结果结构存在性为主，而不是以具体文案内容为主。

## Migration Plan

1. 先基于当前代码确认哪些按钮已经具备真实后端契约，形成动作清单。
2. 补齐 OpenSpec specs，把“按钮反馈”和“上传识别分类闭环”写成独立能力。
3. 在实现阶段优先补高频动作的反馈缺失，以及首页详情区对识别/分类结果的可见性。
4. 为上传确认、Worker 推进、前端状态展示补测试，确保从文件导入到可搜索/可整理的路径可回归验证。
5. 如果实施后发现某些结果字段仍无法稳定提供，可先保留阶段状态与说明文案，再逐步增强真实识别结果展示。

## Open Questions

- 是否需要新增专门的“资产识别详情”接口，还是基于现有 `GET /api/v1/assets/{assetId}` 扩展返回即可满足结果展示？
- 首页详情区是否要直接展示 tags、OCR 摘要和地点结果，还是先只展示状态与 caption 摘要？
- 对“按钮成功反馈”的统一形式，是采用页面级 alert、动作级 toast，还是在按钮邻近区域给出内联确认？当前建议优先采用内联确认或局部状态，避免全局提示过于飘忽。
