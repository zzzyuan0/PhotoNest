## Context

当前 Web 前端由 `app.vue`、`pages/index.vue`、`pages/login.vue` 和 `pages/import.vue` 直接拼出三条主流程，但页面信息架构仍偏向接口联调和能力验证，而不是用户完成任务的路径设计。几个明显问题已经在现状中暴露：

- 首页承载了时间线、地点、重复项、相册、导出、详情查看等过多内容，同时大量标题和说明文案混合了“演示台”“能力验证”“技术术语”，用户难以一眼判断当前页面重点。
- 登录页把“bootstrap 登录、Bearer Token、CSRF、recent auth”等机制性描述直接暴露给用户，主要按钮也没有清楚表达登录成功后的去向与收益。
- 导入页虽然能走上传主流程，但页面组织仍以调试状态为中心，缺少“前置条件 -> 选择文件 -> 上传中 -> 完成后查看”的连续体验。
- 图片查看当前主要依赖列表卡片和滚动到详情区域，浏览、预览、继续操作之间存在较强的上下跳转，查看图片和执行操作不是同一个视觉上下文。

本次变更的约束也比较清晰：

- 当前仓库前端是 Nuxt 4 单页式结构，页面数量少，重构优先应放在页面内结构整理与轻量组件提取，而不是引入庞大的状态管理或设计系统依赖。
- 后端 API 已经覆盖登录、会话读取、导入上传、发现、详情、收藏、相册等核心能力，因此这次设计应尽量复用现有接口，不把问题转移成新的后端需求。
- 用户明确提出要解决“莫名其妙的设计文字”“登录不可理解”“图片无法查看与动线不流畅”，因此设计优先级必须放在内容清晰度、任务导向和查看体验上，而不是单纯视觉换皮。

相关方包括：

- 最终使用者：希望快速完成登录、导入、查看和整理照片，而不需要理解底层认证或上传协议。
- 开发与测试人员：仍然需要看到必要状态，但这些状态应被降级到辅助信息，而不是页面主叙事。
- 后续维护者：需要更清晰的页面边界和可扩展结构，方便继续加组件、补测试和迭代样式。

## Goals / Non-Goals

**Goals:**

- 把顶层导航和首页改造成清晰的任务入口，让用户知道自己现在在“浏览照片”“导入照片”还是“登录授权”。
- 把登录页改造成面向结果的登录体验，明确输入、反馈、当前身份和登录后的下一步。
- 把导入页改造成分步骤上传体验，降低技术术语密度，并让上传完成后自然流向图片查看。
- 把首页图片浏览改造成更稳定的“列表/筛选 + 预览详情 + 直接操作”结构，减少跳转、滚动和上下文断裂。
- 统一页面文案、按钮命名、状态标签、空状态与错误提示，形成一致的轻量照片管理工作台体验。
- 在尽量不新增后端 API 的前提下完成这次前端重构，并为关键状态补上前端测试覆盖。

**Non-Goals:**

- 本次不新增后端接口，也不重构后端认证、上传或发现的数据契约。
- 本次不引入重量级组件库、全局状态管理框架或全新的前端架构层。
- 本次不覆盖移动端专属交互，只要求桌面端优先清晰，并保证小屏幕下仍可正常使用。
- 本次不解决图片编辑、批量拖拽整理或高级图库布局等更重的功能扩展。

## Decisions

### 决策：以“任务导向”的信息架构替换“演示导向”的页面叙事

首页、登录页和导入页统一改为围绕用户任务来组织内容，而不是围绕接口能力说明来写页面文案。标题、副标题、按钮和空状态优先回答“你现在能做什么”“下一步去哪”，技术细节退到次要说明或折叠信息中。

这样做的原因是：当前最大的可用性问题并不是接口缺失，而是页面把内部实现语义直接暴露给用户，导致每个页面都在同时讲“系统怎么工作”和“用户要做什么”。只要主叙事还停留在技术演示层，哪怕按钮功能可用，体验仍会显得混乱。

备选方案：

- 仅替换部分文案，不调整布局：不采用，因为当前问题不仅是文字内容怪，还包括阅读顺序和区域重点失衡。
- 保持现有布局，只增加帮助提示：不采用，因为这会继续在页面上叠加更多说明，反而加重噪音。

### 决策：登录页采用“单目标表单 + 结果摘要 + 下一步动作”结构

登录页将收敛成一个主表单区域和一个轻量结果区域。主区域负责说明为什么要登录、输入什么、登录成功后可以做什么；结果区域只展示与用户相关的关键信息，如当前身份、可访问库和会话状态摘要，并提供“进入照片库”或“去导入照片”的明确跳转。

这样做的原因是：当前登录页把认证机制说明放在了视觉中心，用户读完以后仍然不知道是否应该输入默认账号、是否登录成功，以及登录成功之后下一步去哪。把页内内容改成“输入 -> 反馈 -> 去操作”可以显著降低理解负担。

备选方案：

- 登录成功后自动跳回首页，不显示当前会话摘要：不采用，因为对于当前产品阶段，用户仍需要确认自己登录成了谁、能访问哪些库。
- 继续保留完整会话字段面板：不采用，因为大量技术字段会压过主任务，必要状态应缩成摘要卡片或调试区。

### 决策：导入页采用分步骤上传流，而不是文件状态调试面板

导入页将重构为三段式或四段式流程：准备条件、选择文件、上传进度、完成结果。现有 `entries` 队列和上传状态仍然保留，但 UI 以“步骤 + 当前进度 + 单文件结果”的方式呈现，并在导入完成后给出直接前往照片查看的动作入口。

这样做的原因是：当前导入页虽然功能上完整，但视觉上缺少任务节奏，用户看到的首先是一堆实现细节和状态列表，而不是“我先做什么、系统正在做什么、完成后去哪看”。将它改造成流程型界面可以让上传体验更有把握感。

备选方案：

- 保持当前单页面板，只美化列表样式：不采用，因为核心问题是流程表达不足，不只是样式老旧。
- 把导入改成多页面向导：暂不采用，因为当前页面复杂度尚未高到需要拆分路由，保留单页流程更便于复用现有逻辑。

### 决策：首页采用“双栏工作台 + 原位详情预览”替代滚动式详情跳转

首页将以左侧内容区承载筛选、时间线和结果列表，右侧详情区承载当前选中图片的预览、元信息和快捷操作；在小屏下右侧详情区可退化为抽屉或下展开区域。点击图片后优先在当前上下文中更新详情，而不是把用户滚动到页面深处寻找详情区域。

这样做的原因是：当前首页图片查看的问题不只是“能不能看”，而是用户每次查看详情都在列表和详情区之间发生上下文断裂。把详情固定在同一个阅读框架里，能让“浏览多张图并连续操作”的成本显著下降。

备选方案：

- 使用路由切换到独立详情页：暂不采用，因为当前最需要的是流畅浏览和快速操作，频繁切页会让轻量工作台变重。
- 继续保留底部详情区并自动滚动：不采用，因为自动滚动仍会打断浏览节奏，尤其在筛选和多次切换图片时体验较差。

### 决策：图片预览以“可见性优先”为原则，缩略图未就绪时提供稳定占位与可操作状态

列表和详情都需要显式区分“图片可预览”“图片处理中”“处理失败但资产已存在”等状态。若缩略图令牌未就绪，列表显示统一占位和状态说明；详情区优先展示可读的状态、时间、媒体类型和后续操作，必要时提供受控原图查看入口或等待提示，但不能让用户误解为“没有图片”或“上传失败”。

这样做的原因是：用户已经明确提到“当前图片无法查看”，这里既有真实预览能力的问题，也有状态表达不清的问题。即使某些处理中资源尚未完成，界面也必须让用户知道资产已经存在、系统正在处理、接下来还能做什么。

备选方案：

- 没有缩略图就隐藏该资产：不采用，因为这会让刚上传的照片在界面上像是消失了。
- 对所有状态统一展示同一种灰框：不采用，因为用户无法区分处理中、失败和待加载三种不同情况。

### 决策：保留现有 API 调用模型，但提取轻量 UI 组件与状态映射层

本次不重写 `apiFetch` 调用方式，而是在页面内部提取可复用的轻量组件或组合片段，例如页面头部区、状态徽标、空状态、上传步骤条、资产预览卡、详情面板等，并集中处理文案映射、状态颜色和操作按钮命名。

这样做的原因是：当前问题来自页面过于臃肿、状态字符串直接泄漏到 UI、相同模式重复出现。通过轻量提取和统一映射层，可以在不引入额外依赖的情况下把结构理顺，并为后续迭代留下清晰边界。

备选方案：

- 继续把所有 UI 堆在单个页面文件中：不采用，因为首页和导入页已经足够复杂，继续堆叠会放大维护成本。
- 一次性引入组件库和完整设计 token 系统：暂不采用，因为本次目标是先把主流程体验拉直，不宜把范围扩成基础设施改造。

## Risks / Trade-offs

- [首页信息拆分后，用户可能需要重新适应新位置] → 通过保留核心功能名称、提供清晰分区标题和默认选中详情态来降低迁移成本。
- [不新增后端接口可能限制高质量大图预览方案] → 先通过状态表达、占位策略和现有令牌能力改善“能理解、能继续操作”，必要时把更强预览能力留给后续变更。
- [页面拆分为更多组件后，短期内会增加文件数量] → 控制提取粒度，只抽离高复用和高复杂度片段，避免过度组件化。
- [导入流程更强调步骤后，调试信息可见性会下降] → 将必要的技术状态保留在次级信息区，既不丢调试能力，也不干扰主任务。
- [详情固定在右栏会压缩主列表宽度] → 通过响应式断点在窄屏下切换为抽屉/堆叠布局，保证浏览区不会被过度挤压。

## Migration Plan

1. 先重构 `app.vue` 的顶层导航与全局视觉基础，建立统一页面头部、导航命名和基础状态样式。
2. 重构 `pages/login.vue`，完成登录页文案、反馈区和登录后行动路径整理，并验证现有登录接口行为未受影响。
3. 重构 `pages/import.vue`，把上传主流程改成步骤化界面，保留现有上传逻辑与状态，但调整呈现顺序和完成反馈。
4. 重构 `pages/index.vue`，先拆分筛选/列表/详情区，再补齐图片预览、状态展示和原位操作动线。
5. 补充或更新前端测试，覆盖关键状态映射、登录反馈、上传完成反馈与详情切换行为。
6. 如新界面出现严重可用性问题，可按页面粒度回滚单个文件改动；由于本次主要是前端呈现重构，不涉及数据迁移，回滚风险较低。

## Open Questions

- 详情区中的“大图查看”是否已有后端支持的稳定资源句柄可直接使用？如果当前只有缩略图令牌，则本次先以预览增强和状态说明为主。
- 首页是否要在这次一起弱化“重复项”和“导出”模块的视觉优先级，还是保留但折叠到次级区域？当前建议降级但不移除。
- 登录成功后默认跳转到首页还是导入页，是否应根据是否已有 `libraryId` 决定？当前建议优先跳回首页，并提供显式“去导入”入口。
