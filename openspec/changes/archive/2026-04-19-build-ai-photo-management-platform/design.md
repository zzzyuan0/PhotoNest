## 背景

项目当前还是一个空白的 OpenSpec 工作区，目标是演进成面向个人分散照片库的照片管理平台。目标主流程是：从多个来源导入照片与视频，把原始文件落到对象存储中，通过异步流程补齐元数据和 AI 识别结果，再按时间、地点和内容把资产检索出来，同时通过备份和导出保留独立恢复路径。

这个变更是一个典型的跨层设计，因为它同时引入了存储抽象、统一资产模型、异步处理、搜索索引和用户可见的发现能力。设计上需要兼顾两点：第一版 MVP 不能太重，后续又要保留扩展更多存储 Provider、AI Provider 和前端客户端的空间。

主要相关方包括：
- 终端用户：希望把分散在不同设备和平台里的照片收拢到一个可信主库。
- 运维或部署者：需要可预测的存储、备份和 Provider 配置方式。
- 后续贡献者：需要稳定的内部契约来扩展存储、AI 识别和检索能力。

## 目标 / 非目标

**目标：**
- 定义照片资产、派生资源、元数据、识别状态和备份状态的统一领域模型。
- 将核心职责拆分为存储、元数据、识别增强、检索发现和备份层，并暴露清晰接口。
- 支持可插拔的对象存储和 AI Provider，同时避免把厂商特有返回结构泄漏到领域模型中。
- 支持一版可落地的实现，至少覆盖上传、后台识别、混合搜索和已验证备份。
- 在首版中优先采用模块化单体加后台 Worker，而不是一开始就拆成多个服务。
- 把原图、派生资源、导出包、GPS/OCR 等敏感元数据以及 Provider 密钥纳入统一安全边界，避免通过公网对象、日志、调试信息或外部 Provider 误泄露。

**非目标：**
- 首版不做原生移动端应用。
- 首版不做实时协作分享、评论或社交网络能力。
- 首版不追求人脸识别和实名管理的完美能力。
- 首版不通过非官方接口做 QQ 空间等封闭平台的实时同步。
- 首版不默认引入独立搜索集群，除非 PostgreSQL 方案无法满足需求。

## 设计决策

### 决策：采用模块化单体，并拆分 API 进程与 Worker 进程
第一版实现采用一个代码库、两个运行角色：API 进程负责导入、配置和检索请求，Worker 进程负责异步识别和备份任务。这样可以降低系统拆分带来的协作和运维成本，同时避免长耗时的 AI 与复制任务影响请求延迟。

备选方案：
- 一开始就做微服务：不采用，因为当前没有现成的规模压力，过早拆分会拖慢 MVP 落地。
- 上传时同步完成所有识别：不采用，因为 AI、OCR 和地理反解延迟会让上传流程变慢且脆弱。

### 决策：前端采用 Vue 生态，并以 Nuxt 作为首个 Web 客户端框架
首个用户可见客户端采用基于 Vue 3 的 Nuxt 应用，用来承载上传入口、时间线浏览、地点浏览、自然语言搜索、重复照片审查和设置页面。Nuxt 负责页面路由、混合渲染、会话边界和少量 BFF 能力，但核心业务规则、导入状态机、Provider 配置和搜索编排仍放在 Go API 中，避免前端承担领域事实来源。

前端数据分层采用“服务端状态”和“界面状态”分离的方式：与资产列表、导入状态、搜索结果、分页游标相关的服务端状态优先通过 `TanStack Query for Vue` 管理；筛选面板开关、批量选择和局部 UI 偏好等界面状态由 `Pinia` 或 Vue 组合式状态方案承载。这样可以降低时间线、搜索和长列表界面的状态耦合。

备选方案：
- 裸 Vue + Vite 自建 SSR：不采用，因为上传、路由守卫和服务端渲染边界都需要额外基础设施，MVP 不值得为此承担更多脚手架维护成本。
- 继续选择 React / Next.js：不采用，因为当前更倾向于 Vue 技术栈，而且本项目的核心后端不会依赖 React 生态特有的全栈能力。

### 决策：后端采用 Go 模块化单体，并拆分 HTTP API 与后台 Worker
后端采用 Go 作为主要实现语言，并继续坚持模块化单体思路。API 与 Worker 为两个独立运行角色，但共享相同的领域模型、Provider 契约、任务定义和数据库访问层。HTTP 层优先采用贴近标准库、易于组合的轻量路由方案，参考实现默认选择 `chi`；如果后续更偏向快速脚手架，也可以在保持模块边界不变的前提下替换为 `Gin`。

这样做的原因是：对象存储访问、分片上传确认、备份复制、批量导入、任务消费和并发控制都非常适合 Go；同时单二进制部署、资源占用和运维复杂度也更符合 MVP 阶段的需求。

备选方案：
- 前后端全部使用 TypeScript：不采用，因为团队当前可以接受跨语言栈，并且 Go 在 I/O 密集和后台编排场景下更有优势。
- 一开始拆成独立导入服务、检索服务和备份服务：不采用，因为当前还不需要用服务拆分来换取独立扩容或团队边界。

### 决策：以前后端契约优先于共享语言类型
由于前端采用 Vue，后端采用 Go，因此不把“共享语言类型”作为架构前提，而是通过稳定的 HTTP 契约维持边界。MVP 阶段优先采用 OpenAPI 驱动的接口定义方式，对外 API 使用显式 DTO、分页结构、错误模型和枚举约束，前端基于生成的 TypeScript Client 调用 API，避免手写请求结构逐渐漂移。

内部领域模型、数据库实体和对外响应模型保持解耦。这样即使未来增加桌面导入器、CLI 工具或其他客户端，也可以复用同一套对外契约，而不需要依赖共享运行时语言。

备选方案：
- 前端直接手写 `fetch` 请求和本地类型：不采用，因为随着搜索、备份、导入和状态轮询变复杂，接口演进会更容易失控。
- 首版采用 GraphQL：不采用，因为上传、长任务状态、对象存储预签名和运维配置本身更适合明确的命令式 HTTP 接口。

### 决策：以 PostgreSQL 作为元数据和检索编排的事实来源
PostgreSQL 用来存储统一资产记录、导入会话、Provider 配置、识别状态、相册关系和备份元数据。MVP 阶段默认结合 `pgvector` 做语义相似度，结合 PostgreSQL 全文检索 captions、OCR 文本和 tags，并辅以 `pg_trgm` 类似扩展增强模糊匹配能力，从而在不引入外部搜索集群的前提下提供混合搜索能力。

备选方案：
- 首版直接引入 Elasticsearch 或 OpenSearch：不采用，因为运维成本较高，对 MVP 规模并非刚需。
- 只把可检索信息存到对象存储 metadata：不采用，因为跨 Provider 查询能力过弱，而且不同厂商行为不一致。

### 决策：数据库访问以原生 SQL 能力为中心
后端数据库访问优先采用接近原生 PostgreSQL 的方式组织，而不是先围绕重量级 ORM 建模。参考实现优先选择 `pgx` + `sqlc` 这一类 SQL-first 方案，因为本项目的核心查询高度依赖 PostgreSQL 特性，包括全文检索、向量检索、时间聚合、重复候选查询、备份校验和多阶段状态筛选。相比抽象程度较高的 ORM，这类查询更适合通过清晰、可审查的 SQL 来表达，并在生成的类型安全访问层中复用。

数据库迁移、索引定义和扩展启用也应被视为一等资产，与 Go 代码一起版本化管理。这样可以确保 `pgvector`、`tsvector`、`pg_trgm` 以及后续可能出现的表达式索引都能被稳定演进。

备选方案：
- 以通用 ORM 作为主要访问入口：不采用，因为复杂搜索和聚合逻辑最终仍会大量回落到原生 SQL，反而会造成两套抽象并存。
- 把搜索所需字段单独同步到外部搜索库后再查询主库：不采用，因为这会在 MVP 阶段额外引入一致性与运维成本。

### 决策：持久化 Provider 无关的资产身份与对象引用
每个资产都拥有统一的 `asset_id`、内容哈希、感知哈希，以及一组对象引用。对象引用负责记录 Provider 名称、bucket 或 container、对象 key、版本或 etag，以及 `original`、`thumbnail`、`preview` 等用途。系统不会把 Provider 的原始响应体当作事实来源。

备选方案：
- 直接把 Provider key 当作主标识：不采用，因为这会让迁移、备份和多 Provider 支持变得脆弱。
- 每个资产只保留一条原图路径：不采用，因为备份、导出和恢复流程都需要维护多个对象引用。

### 决策：首版对象存储以腾讯云 COS 为生产参考实现
虽然系统在抽象层继续保持对 S3 兼容对象存储的扩展能力，但 MVP 首版明确把腾讯云 COS 作为生产环境和默认开发路径的优先支持目标。对于已经拥有可用 COS bucket 的部署者，系统不要求额外构造一套独立的 S3 存储；开发和测试环境仅在没有云账号或需要离线联调时，才使用 S3 兼容模拟器作为可选替代方案。

选择腾讯云 COS 的原因是：项目首版面向中文用户和国内部署场景，优先明确一个可直接落地的云对象存储目标，比“抽象上支持很多 Provider，但没有首发落点”更有执行价值。同时，腾讯云官方文档明确提供了兼容 S3 的接入方案，这让系统可以在不牺牲统一存储契约的前提下，把 COS 作为首版重点支持对象。

需要注意的是，“兼容 S3”不等于所有行为都可以完全按 AWS S3 心智直接假设。配置层仍然要显式建模 COS 所需的地域、bucket、endpoint、认证信息、对象 key 前缀、预签名上传、CORS 前置条件和分片上传校验流程，并在启动阶段完成可写性检查。

备选方案：
- 首版只写“支持任意 S3 兼容存储”而不指定生产参考实现：不采用，因为会让部署文档、联调路径和验收范围变得模糊。
- 首版同时承诺多个云厂商对象存储为一等支持：不采用，因为当前项目还处于 MVP 阶段，应先把一个明确的生产目标跑通。

### 决策：上传链路采用直传对象存储，API 只负责会话与确认
浏览器上传优先采用“服务端创建导入会话并签发预签名，前端直传腾讯云 COS，上传完成后再调用确认接口”的方式。Go API 负责创建导入会话、分配对象 key、签发预签名信息、校验上传结果并入队后续任务；对象字节本身不经过 API 进程中转，除非是在本地目录导入等受控场景下由内部导入器执行。

这样可以降低 API 带宽压力，并让大文件、视频和分片上传的行为与对象存储能力保持一致。对后续接入多客户端也更友好，因为“对象上传”和“元数据登记”从一开始就是解耦的。

这个上传状态机必须满足三个约束：
- 对象 key 由服务端分配，前端不能自行决定最终存储路径。
- 浏览器在收到预签名后直接把字节写入 COS，但只有在“确认上传”成功后，资产才会被标记为已接收并进入后续处理。
- 确认阶段必须通过统一存储契约执行对象存在性校验，并比对大小、etag 或等价校验信息，避免把未完成或错传的对象误记为已入库资产。

在首版实现中，生产环境的预签名上传和分片上传流程默认围绕腾讯云 COS 验证；本地开发仅在需要无云账号联调时，通过 S3 兼容模拟器复现相同接口契约，确保上传状态机不依赖单一云环境才能开发。

推荐的数据流如下：

```text
前端
  │ 1. 创建导入会话
  ▼
Go API
  │ 2. 分配对象 key 并签发预签名
  ▼
腾讯云 COS
  ▲ 3. 浏览器直传原始文件
  │
前端
  │ 4. 调用确认上传接口
  ▼
Go API
  │ 5. 校验对象存在性与会话匹配关系
  ▼
Worker
```

备选方案：
- 所有上传都先经过 API 再转存：不采用，因为大文件会明显放大应用层带宽和内存压力，也不利于后续做断点续传或多分片上传。
- 前端自己决定对象键并直接上传：不采用，因为对象身份、权限和导入会话需要由服务端统一分配和审计。

### 决策：默认以私有对象访问和短时授权读取保护照片资产
首版把原图、缩略图、预览图、导出包和备份工件都视为敏感资产，默认要求对象存储保持私有读，不提供可长期复用的公网 URL。面向 Web 客户端的读取路径由 Go API 执行认证授权后再返回受控响应，可以是 API 直接代理，也可以是分钟级有效期、单对象作用域的短时签名 URL。对象 key 必须由服务端生成且保持不透明，不能直接暴露原始文件名、地点、相册名或用户输入片段，从而降低对象枚举与 URL 扩散风险。

这项决策同时覆盖浏览态的缩略图与预览图，而不仅仅是原图下载。否则系统即使没有暴露原始对象，也可能通过公开缩略图、稳定导出链接或可猜对象键形成同样严重的照片泄露面。

备选方案：
- 允许缩略图或预览图使用公共读 CDN URL 以换取更简单的前端实现：不采用，因为缩略图本身就足以暴露拍摄对象、地点和时间线信息。
- 用可预测的对象层级表达相册名和文件名以方便运维排查：不采用，因为可读 key 会增加对象枚举、日志外流和分享误传风险。

### 决策：认证、授权、审计作为一等能力建模
虽然项目首版不强绑定单一身份提供方，但应用层必须形成稳定、可审计的主体身份和会话边界。可接受的首发实现包括本地管理员登录、OIDC 接入或受信反向代理注入身份；无论采用哪一种，对时间线、检索、详情、下载、导出、Provider 配置、隐私策略调整等接口都必须执行认证与授权，不能假设“部署在内网”就足够安全。

对高风险操作还需要额外保护。像整库导出、批量下载、修改 Provider 凭据、切换隐私策略、查看调试保留数据等动作，除了基础会话校验，还应支持近期认证、显式确认和审计事件，以便在照片库被误用或账户被借用时保留可追溯路径。

备选方案：
- 完全依赖反向代理或 VPN 作为唯一访问控制：不采用，因为应用层仍然需要判断谁在访问哪类资产，以及谁触发了导出或配置变更。
- 只记录基础访问日志，不为敏感动作建立审计模型：不采用，因为照片库的高风险操作需要可追溯的主体、对象和结果信息。

### 决策：密钥、预签名信息和调试数据必须最小暴露
Provider 配置中的认证信息、访问密钥、API Token 和等价秘密值应优先通过环境变量、Secret Manager 引用或加密存储注入，避免以明文散落在数据库、配置文件和接口响应中。即使系统需要在 PostgreSQL 中保存 Provider 配置，也应把密钥字段视为密文或外部引用，而不是普通字符串。任何 API 响应、结构化日志、指标标签、trace、死信任务载荷和健康检查结果都不得输出完整密钥、Token、预签名 URL 或可直接复用的请求头。

与此类似，调试信息也必须最小化。对象存储错误上下文、AI Provider 错误回包、OCR 文本、原始 GPS 坐标和导出 manifest 片段都可能成为泄露源，因此默认不保留原始 Provider 响应；若为了问题排查临时开启调试保留，也必须附带管理员权限、自动过期时间和显式清理路径。

备选方案：
- 为了便于排查问题，把完整请求、完整响应和预签名信息直接写入日志：不采用，因为这会把照片系统最敏感的数据主动复制到更多系统里。
- 为了方便运维，把 Provider 密钥作为普通配置项直接展示在管理界面中：不采用，因为界面截图、浏览器缓存和错误上报都会扩大泄露面。

### 决策：将 AI 返回结果归一化为内部识别记录
不同 AI Provider 的返回结构差异很大，因此 Worker 层必须将其映射为统一的识别记录，例如 captions、tags、OCR blocks、embeddings，以及可选的人脸或主题聚类。Provider 原始响应可以保留用于调试，但发现层和后续流程只能依赖归一化字段。

备选方案：
- 直接以 Provider 返回结构作为主元数据：不采用，因为 Provider 间 schema 漂移会把复杂度扩散到检索、备份和导出逻辑里。
- 首版只支持单一 AI 厂商：不采用，因为隐私、成本和地区可用性本来就是这个产品的重要约束。

### 决策：敏感元数据和外部 AI 出站受隐私策略控制
照片库不仅要保护原图本身，也要保护由系统衍生出的隐私副本。GPS 坐标、地点解析结果、OCR 文本、caption、tag、embedding，以及未来可能出现的人脸或主题聚类，都应被视作敏感元数据。系统需要支持库、相册或资产级别的隐私策略，用来控制哪些阶段允许远程 Provider 处理，哪些结果可以持久化，哪些字段可以在发现层和导出流程中返回。

这意味着“识别增强成功”不等于“所有结果都应无条件长期保存”。例如某些相册可能允许本地 EXIF 提取，但禁止远程 OCR 或地理反解；另一些资产可以参与全文检索，但不应在一般列表响应中暴露原始坐标或 OCR 全文。策略拒绝本身也应成为显式状态，以便用户理解为什么某些识别阶段未运行。

备选方案：
- 默认对全部资产执行远程 AI 识别并长期保存所有中间结果：不采用，因为这会放大对外数据暴露和敏感元数据堆积风险。
- 只在 UI 层隐藏敏感字段，但在导出和日志里继续完整保留：不采用，因为这无法真正缩小泄露面。

### 决策：采用分阶段、可重试、幂等的后台任务状态机
资产处理按明确阶段推进，例如 `accepted`、`stored`、`derivatives_ready`、`metadata_ready`、`ai_ready`、`indexed` 和 `partial_failure`。每个后台任务都必须幂等且可重跑，确保重试不会产生重复对象或重复元数据记录。

备选方案：
- 用一个大而全的“处理资产”任务串行完成全部步骤：不采用，因为部分失败的恢复路径会变得不透明。
- 后台任务只做 best-effort，不跟踪状态：不采用，因为用户需要看到索引进度，运维也需要确定性的重试机制。

### 决策：后台任务采用 Redis 驱动队列，由 Go Worker 分阶段消费
MVP 采用 Redis 驱动的任务队列来承载异步处理，并由独立的 Go Worker 消费。参考实现优先选择 `Asynq` 这类成熟的 Redis 队列库。队列按阶段或任务类型拆分，例如导入后处理、派生资源生成、EXIF 提取、地理反解、caption、OCR、embedding、索引更新和备份复制。每个任务都带有稳定的幂等键、重试策略、错误分类和关联资产标识。

这种方案的优点是实现成本低、运行模型清晰，足以覆盖 MVP 对重试、延迟任务、并发消费和死信观测的需求。Worker 只通过数据库和对象存储写入事实状态，而不会依赖内存中的链式上下文。

备选方案：
- 采用 Temporal 一类工作流引擎：暂不采用，因为引入额外控制面和心智负担，对 MVP 来说偏重。
- 采用跨语言任务系统并把主流程建立在 Python Worker 上：不采用，因为当前后端主实现语言已定为 Go，首版应优先控制系统边界复杂度。

### 决策：本地 AI 推理通过独立扩展位接入，而不是让 Go 直接承担模型生态
首版默认把 Go 视为编排层和控制面：负责任务路由、状态流转、Provider 策略和结果归一化。若后续需要本地 OCR、embedding 或 caption 模型，则通过独立 sidecar、独立推理服务，或命令行工具包装的方式接入，而不是要求 Go 直接承载主要模型运行生态。

这样既保留了未来接入 Python 推理栈或本地模型框架的空间，也能让当前 MVP 把主要精力放在资产模型、导入链路、检索和备份这些系统骨架上。

备选方案：
- 首版就把本地模型推理作为后端核心职责：不采用，因为这会显著抬高环境搭建、依赖管理和跨平台部署复杂度。
- 完全不预留本地 AI 扩展位：不采用，因为隐私策略和成本控制本身就是该产品的重要约束。

### 决策：通过统一查询模型实现混合发现
发现层查询会把结构化过滤、全文匹配和向量相似度整合到一个查询服务中。查询层根据可用信号生成综合排序，并在某个资产尚未完成全部识别阶段时做平滑降级。

备选方案：
- 把元数据搜索和语义搜索拆成两个独立接口：不采用，因为用户应该能用一句自然语言完成一次完整检索。
- 未完成识别的资产全部从浏览和搜索结果中隐藏：不采用，因为刚上传的照片也必须立即出现在主库视图里。

### 决策：把备份当作一等工作流，而不是额外附加项
备份要被建模为独立的复制工作流，拥有自己的目标 Provider、manifest 条目、校验状态和重试历史。只有当复制副本通过源资产身份与完整性校验之后，资产才会被标记为已受保护。

备选方案：
- 完全依赖主存储自身的高可用：不采用，因为用户诉求本身就要求独立恢复路径。
- 只提供手动导出，不做持续复制：不采用，因为手动导出无法及时保护新增资产。

### 决策：导出与备份按高风险外流通道设计
导出包、恢复 manifest 和备份副本本质上都是“把照片库复制到别处”的能力，因此默认按高风险外流通道设计。导出请求必须经过认证授权，并记录审计事件；交付导出工件时，应优先采用加密归档包、受控存储目标或短时下载链接，避免产生可长期传播的明文归档 URL。manifest 需要支持最小恢复所需的完整版本，也应允许生成脱敏版本，用于演练、排障或外部核对时减少 GPS、OCR 和内部对象引用的扩散。

备份目标也不能被默认为“天然可信”。主库存储与二级备份的权限、访问域和生命周期策略应相互独立，并延续私有读要求，防止因为备份桶、导出目录或恢复中间产物配置宽松而绕过主库的访问控制。

备选方案：
- 把导出包当作普通静态文件处理，只要生成成功就长期保留下载地址：不采用，因为导出包通常是最容易被误分享和二次传播的工件。
- 认为备份目标只供运维使用，因此无需延续主库的私有读和审计约束：不采用，因为备份侧往往承载的是更完整、更少约束的数据副本。

### 决策：导入来源保持明确且可控
MVP 支持上传、本地目录导入和历史导出包导入。像 QQ 空间这类封闭平台，首版只支持用户自行导出后再导入，不做非官方在线抓取，从而降低维护成本和法律风险。

备选方案：
- 首版就为所有消费级平台做直接同步适配器：不采用，因为脆弱的非官方集成会过早吞掉项目精力。

## 运行时拓扑

推荐的首版运行时与目录边界如下：

```text
.
├── apps/
│   └── web/                # Nuxt 应用，负责上传、浏览、搜索和设置
├── cmd/
│   ├── api/                # Go HTTP API 入口
│   └── worker/             # Go 后台任务入口
├── internal/
│   ├── asset/              # 资产、对象引用、派生资源
│   ├── ingestion/          # 导入会话、上传确认、去重
│   ├── enrichment/         # EXIF、地理反解、AI 归一化
│   ├── discovery/          # 时间线、地点浏览、混合搜索
│   ├── backup/             # 复制、校验、manifest、恢复规划
│   ├── provider/           # 对象存储与 AI Provider 契约及适配器
│   ├── job/                # 队列任务定义、消费器、调度
│   └── platform/           # 配置、日志、观测、HTTP 中间件
└── db/
    ├── migrations/         # PostgreSQL 迁移
    └── queries/            # SQL 查询定义与生成代码输入
```

对应运行关系如下：

```text
浏览器 / 导入客户端
        │
        ▼
    Nuxt Web
        │
        ▼
      Go API
   ┌────┼──────────────┬──────────────┐
   ▼    ▼              ▼              ▼
Postgres Redis     Object Storage   AI Providers
   ▲    ▲              ▲
   └────┴────── Go Worker ───────────┘
```

这套拓扑的关键原则是：
- Web 客户端不是领域事实来源，只负责交互和少量会话边界。
- Go API 是导入、检索、配置和任务编排入口。
- Go Worker 负责耗时处理、状态迁移和副作用操作。
- PostgreSQL 持有事实数据，Redis 承载异步调度，对象存储持有原始与派生二进制资产。

## 风险 / 权衡

- [仅使用 PostgreSQL 的混合搜索效果可能不够强] -> 缓解：保留搜索适配层边界，后续可以无痛接入独立搜索引擎。
- [大规模照片库下 AI 调用成本可能快速上升] -> 缓解：记录每个任务的 Provider 选择，允许关闭高成本阶段，并支持按相册设置本地优先策略。
- [后台任务重试如果设计不当会造成状态不一致] -> 缓解：强制任务幂等，显式维护阶段迁移，并在写入前做对象级身份校验。
- [地理反解和 AI 识别会带来隐私风险] -> 缓解：允许按任务类型配置 Provider 策略，支持仅本地处理，并阻止敏感资产发送到不允许的外部 Provider。
- [大批量导入时备份副本可能明显滞后] -> 缓解：在资产模型里暴露备份状态，只有通过校验后才标记为已保护。
- [历史来源较乱时元数据可能不完整] -> 缓解：保留导入时间戳和来源信息，让发现层优先使用“最佳可用时间”而不是让导入失败。
- [前后端采用不同语言后，接口契约可能漂移] -> 缓解：坚持 OpenAPI 驱动的接口描述、生成前端 Client，并增加契约级测试。
- [Go 生态对本地多模态模型支持不如 Python 成熟] -> 缓解：把本地 AI 视为独立扩展位，通过 sidecar 或独立服务接入，而不是让主后端直接耦合模型运行时。
- [直传对象存储后，上传完成与资产登记可能出现时序问题] -> 缓解：通过导入会话、上传确认接口和对象存在性校验来闭合状态机，避免把未确认对象误认为已入库。
- [对象存储、备份桶或缩略图资源被误配置为公共读] -> 缓解：启动阶段检查公开读风险，默认私有读，并只通过认证接口或短时签名暴露读取能力。
- [日志、trace、队列载荷或调试数据复制出密钥、预签名 URL、OCR/GPS 等敏感内容] -> 缓解：建立统一脱敏策略，禁止输出完整秘密值，并限制原始 Provider 响应的保留范围与时长。
- [导出包和恢复 manifest 成为最易扩散的高价值副本] -> 缓解：导出走显式授权、审计、短时访问或加密归档，并支持脱敏 manifest。

## 迁移计划

1. 建立 Nuxt Web、Go API、Go Worker、数据库迁移和 SQL 查询目录结构，以及本地开发编排。
2. 引入统一数据库 Schema、Provider 配置模型、对象引用模型、隐私策略模型与 OpenAPI 接口骨架，并确定密钥引用或加密存储边界。
3. 建立认证会话、授权检查、审计事件和默认私有读边界，先把读取与敏感操作安全地收口。
4. 实现主导入流程，完成导入会话、服务端预签名、前端直传 COS、上传确认、原始对象登记以及派生资源生成。
5. 增加 Worker 驱动的元数据提取、AI 识别、索引更新和清晰处理状态，并落实外部 Provider 出站策略与调试保留边界。
6. 增加时间线、地点浏览、重复照片审查和混合搜索等发现能力，同时确保发现层返回字段与下载路径遵守授权和最小暴露原则。
7. 增加二级备份复制、完整性校验、导出清单和恢复导向的打包能力，并补齐导出审计、受控访问或加密交付。

回滚策略：
- 关闭新的导入入口，同时保留已存储的原图和元数据。
- 停止 Worker 消费，冻结识别和备份流程，而不删除源资产。
- 如果后续需要重构，可先从 PostgreSQL 导出已保存的元数据和对象引用。
